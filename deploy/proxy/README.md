# Витрина на titanvps.pro

Задача: покупатель заходит на `titanvps.pro`, а имя
`vbotrouters.titanvps.click` и адрес сервера с приложением
(`82.197.73.251`) не видит никто.

**Записи в DNS не меняются ни одной.** `titanvps.pro` уже резолвится
на `5.34.214.243` — туда и ставится прокси. Меняется не то, куда ведёт
имя, а то, кто отвечает на запрос с этим именем.

```
клиент ──443──▶ 5.34.214.243 (titanvps.pro)
                 │  nginx stream, читает SNI
                 ├─ titanvps.pro ─▶ nginx http ──▶ 82.197.73.251:8443
                 │                                 приложение, порт закрыт
                 │                                 файрволом на 5.34.214.243
                 └─ всё остальное ─▶ remnanode, как было
```

Приложение никуда не переезжает — переезжает только адрес, по которому
его видит покупатель.

## Почему через SNI, а не обычным vhost

На `5.34.214.243` живёт remnanode и держит 443 целиком: на неузнанный
запрос она отдаёт камуфляж — сертификат `amd.com`. Обычный vhost рядом
не встанет, порт один. Поэтому впереди ставится `ngx_stream_ssl_preread`:
он читает имя из приветствия TLS, **не расшифровывая** его, и разводит
по двум адресам. Для ноды это остаётся прозрачным TCP, Reality не ломается.

Умолчание в карте имён — нода: незнакомое имя обязано вести себя как
раньше, иначе мы своими руками сделаем её заметной.

## Что прячет origin, а что нет

Сам по себе прокси **не прячет ничего**: пока `vbotrouters.titanvps.click`
резолвится, адрес приложения берётся одной командой `dig`. Прячут три
вещи вместе:

1. **DNS.** Старое имя снимается с записи — шаг 5, последний.
2. **Сертификат.** Публичное имя попадает в CT-логи, открытый журнал всех
   выписанных сертификатов; его просматривают поиском по домену. Поэтому
   origin переходит на самоподписанный: публичного имени у него больше
   нет, выписывать нечего.
3. **Ссылки в приложении.** Фото каталога, баннер, картинки витрины
   собираются из `API_PUBLIC_BASE_URL`. Не поменять — витрина покажет
   старое имя в адресе первой же картинки.

Плюс сеть: пока 8443 на origin открыт всем, прокси обходится сканированием.

## Порядок

Шаг 2 — единственный ломающий, и ломает он **не витрину, а клиентов
ноды**: на время между шагами 2 и 4 у них не отвечает 443. Делать 2, 3
и 4 подряд.

### 1. Подготовить origin

Ничего не ломает, старый адрес продолжает работать.

Самоподписанный сертификат — публичного имени у сервера больше не будет,
значит и в CT-логах его не будет:

```bash
mkdir -p /opt/router-shop/deploy/origin-tls && cd /opt/router-shop/deploy/origin-tls && openssl req -x509 -newkey rsa:2048 -nodes -days 3650 -keyout origin.key -out origin.crt -subj "/CN=titanvps.pro" -addext "subjectAltName=DNS:titanvps.pro,DNS:cdn.titanvps.pro"
```

Ключ в репозиторий не попадает — каталог в `.gitignore`. Второе имя
в SAN стоит с запасом под списки и прошивки: перевыпускать сертификат
потом — это ещё и копировать его заново на прокси.

Приложение поднимается со своим nginx на 8443; 80 и 443 остаются чужому
Caddy, он на этом сервере не один:

```bash
cd /opt/router-shop && sed -i 's|^COMPOSE_FILE=.*|COMPOSE_FILE=docker-compose.yml:docker-compose.origin.yml|' .env && grep '^COMPOSE_FILE' .env
```

```bash
cd /opt/router-shop && git pull --ff-only && docker compose up -d --remove-orphans
```

Порт открывается только для прокси:

```bash
ufw allow from 5.34.214.243 to any port 8443 proto tcp && ufw deny 8443/tcp
```

`deploy/origin-tls/origin.crt` скопировать на прокси в
`/etc/nginx/origin-ca.pem` — он понадобится на шаге 4.

### 2. Освободить 443 у ноды

**Разведано 31 августа, и это не так просто, как ожидалось.** Контейнер
`remnanode` работает в `network_mode: host`, публикации портов у него нет
вовсе — Xray слушает `*:443` напрямую:

```
LISTEN *:443  users:(("rw-core",pid=188919))
LISTEN *:443  users:(("xray-linux-amd6",pid=756656))
```

Менять в compose нечего: порт приходит из конфига, который отдаёт панель
Remnawave, и локальная правка будет затёрта следующей синхронизацией.
Публичный адрес у ВМ один — `5.34.214.243`, второго интерфейса нет.

Значит, вариантов ровно три, и выбор за владельцем ноды:

1. **Перенести инбаунд ноды на 8444 в панели Remnawave.** Правильное место,
   nginx забирает 443. Цена — подписки у клиентов перевыпускаются, и те,
   чей клиент не обновляет подписку сам, отвалятся до ручного обновления.
2. **Второй IP у провайдера.** Ноду не трогаем совсем, витрина слушает 443
   на втором адресе. Но `titanvps.pro` придётся перевести на него — а это
   правка DNS-записи, от которой отказались; и если у клиентов в конфигах
   стоит это имя, они уедут вместе с записью.
3. **Витрина на другом хосте, под поддоменом.** Ничего здесь не трогаем
   вообще, но имя будет не apex.

До решения дальше идти нельзя: шаги 3–4 предполагают, что 443 свободен.

### 3. Сертификат для витрины

```bash
apt update && apt install -y nginx certbot
```

```bash
certbot certonly --standalone -d titanvps.pro
```

`--standalone` берёт 80. Если его занял nginx — `systemctl stop nginx`
перед выпуском.

### 4. Включить nginx

`stream-sni.conf` → `/etc/nginx/stream.d/`, `shop-site.conf` →
`/etc/nginx/conf.d/`. В `/etc/nginx/nginx.conf` на верхнем уровне,
рядом с `http {}`, а не внутри:

```
stream {
    include /etc/nginx/stream.d/*.conf;
}
```

Подставить адрес origin и поднять:

```bash
sed -i 's/ORIGIN_IP/82.197.73.251/' /etc/nginx/conf.d/shop-site.conf && nginx -t && systemctl reload nginx
```

**Сразу же проверить, что нода вернулась:**

```bash
openssl s_client -connect 127.0.0.1:443 -servername amd.com </dev/null 2>/dev/null | openssl x509 -noout -subject
```

Должен быть `amd.com`. Если нет — вернуть ноде публикацию `443:443`
и разбираться, клиенты ждать не будут.

Дальше витрина:

```bash
curl -s https://titanvps.pro/ | head -20
```

### 5. Переписать адрес в приложении и убрать старое имя

На origin:

```bash
cd /opt/router-shop && sed -i 's|^API_PUBLIC_BASE_URL=.*|API_PUBLIC_BASE_URL=https://titanvps.pro|' .env && make deploy
```

Бот и веб-админка ходили к API через публичный домен, то есть через чужой
Caddy. Оверлей публикует API на петле — перевести их туда:

```bash
systemctl cat router-bot | grep EnvironmentFile
```

```bash
sed -i 's|^FLEET_API_URL=.*|FLEET_API_URL=http://127.0.0.1:8000|' <файл окружения> && systemctl restart router-bot router-webadmin
```

И только после того, как по новому адресу прошёл целиком заказ — каталог,
оплата, карточка, — снять `vbotrouters.titanvps.click` с DNS и убрать его
блок из Caddy на origin.

Имя останется в CT-логах навсегда: сертификат уже выписан, запись оттуда
не убирается. Но без DNS адрес по нему не берётся.

## Проверка

```bash
curl -s https://titanvps.pro/ | grep -o "82\.197\.73\.251\|titanvps\.click" | sort -u
```

Пусто — ни адреса, ни старого имени в выдаче нет.

```bash
dig +short vbotrouters.titanvps.click
```

Пусто — записи нет.

```bash
curl -sk --max-time 5 https://82.197.73.251:8443/healthz || echo "порт закрыт"
```

## Что осталось на потом

* **Списки и прошивки.** В этот заход не входят: роутеры тянут списки
  со старого `vm171085`, адрес манифеста в прошивку ещё не прописан.
  Но адрес им нужен **до выпуска партии** — зашитый в образ он меняется
  только перевыпуском. Заготовка под второе имя `cdn.titanvps.pro` —
  в комментариях конфигов, в SAN сертификата origin оно уже есть.
* **Вебхук Platega** — адрес колбэка в личном кабинете провайдера. Сейчас
  колбэк уходит на сторону другого бота, а статус мы узнаём опросом, так
  что переезд его не задевает; но если колбэк переведут на нас, адрес
  должен быть новый.

## Откат

Убрать конфиги из `/etc/nginx/conf.d/` и `/etc/nginx/stream.d/`, вернуть
ноде публикацию `443:443`, поднять её. На origin — `COMPOSE_FILE` без
оверлея. Пока старое имя не снято с DNS, витрина остаётся доступной
по нему, и откат — это просто «перестать пользоваться новым».
