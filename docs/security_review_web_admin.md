# Ревью безопасности: bot/web_admin/ (кроме routes/payments.py)

Read-only аудит. Файлы не менялись (`git status` чист). Зона: `bot/web_admin/**`
кроме `routes/payments.py`. Просмотрены `run.py` целиком, все `routes/*.py`,
все `core/*.py`, шаблоны на `|safe`.

## TL;DR

**CRITICAL: 4, MAJOR: 8, MINOR: 7**

Главный вывод: у стороннего продукта в целом крепкая модель (сессии, IP-whitelist,
параметризованный SQL везде), но роль «модератор» протекает в нескольких местах —
от полного обхода до эскалации через XSS. Отдельно — регресс по багу
из журнала («таймауты массовых действий чинили»): в `bulk_ops.py` таймаут
поставили только одному из пяти инструментов, остальные снова могут зависнуть
навечно и заблокировать все bulk-операции разом общим локом.

## CRITICAL

**[CRITICAL] bot/web_admin/run.py:462-490 (`_path_to_section` в `_admin_auth_guard`)
— модератор обходит раздельные права и получает root-пароль роутера, консоль,
рассылку и рестарт сервисов**
Карта путь→раздел для модератора не содержит записей для `/routers`, `/stock`,
`/catalog`, `/orders` (склад/роутеры/каталог/заказы перенесены из нашей админки
позже, чем писалась эта карта) — при `req_section=None` код падает на `'dashboard'`
(строка 480-481), а `dashboard` есть в списке разделов модератора по умолчанию
(`settings.py:317`, `'["dashboard","users","payments"]'`) и вообще не имеет
тумблера в UI (`settings_general.html` перечисляет только
dashboard/users/payments/analytics/bonuses/tariffs/tools/updates).
Отдельно — substring-мэтчинг ломается на `/send_news` (`'/news' in path` не
матчит, т.к. слэша перед `news` нет) и на `/restart_all`, `/restart_services`
(`'/services' in path` не матчит `restart_services`) — оба падают туда же,
в `dashboard`.
**Сценарий:** модератор (роль задумана как «ограниченный» — например, только
раздел «Платежи») логинится и напрямую открывает
`POST /{secret}/routers/<id>/ssh-password` — получает root-пароль клиентского
роутера; `POST /{secret}/routers/<id>/console` — исполняет произвольную команду
на роутере через fleet API; `POST /{secret}/send_news` — рассылает вложение
до 50 МБ всей базе клиентов; `POST /{secret}/restart_all` — `sudo systemctl
restart router-bot.service` (DoS). Ни один из этих разделов админ ему не выдавал.
**Фикс:** добавить явные записи в `_path_to_section` для новых разделов
(`/routers`→`devices`, `/stock`→`devices`, `/catalog`→`shop`, `/orders`→`shop`,
`/send_news`→`tools`, `/restart_`→`tools`), и при `req_section is None`
по умолчанию **блокировать** (`403`), а не отдавать `dashboard`.

**[CRITICAL] bot/web_admin/routes/api.py (весь файл), `_api_require_login`
(строки 37-60) — api_bp вообще не проверяет роль/раздел, только факт логина**
`admin_bp` (страницы) режет модератора по разделам в `run.py`, но `api_bp`
(`/{secret}/api/*`) — отдельный blueprint со своим `before_request`, который

нескольких ручных `if session.get('admin_role') == 'moderator': return 403`
в единичных местах (`api.py:1832` — отмена платежа, `api.py:2092` —
bulk-delete-users, `api.py:2359` — загрузка фото помощи). Всё остальное —
`POST /api/users/<id>/toggle-block`, `POST /api/delete_empty_uuid_users`
(безвозвратное массовое удаление пользователей без UUID), `POST
/api/remnawave/add-traffic` / `reduce-traffic` / `set-squad`,

**Показательная асимметрия:** `/api/bulk-delete-users` явно блокирует модератора,
а `/api/delete_empty_uuid_users` (тот же по сути эффект — массовое необратимое
удаление) — нет.
**Фикс:** завести общий декоратор/проверку роли в `api_bp.before_request` по
той же карте разделов, что использует `admin_bp`, либо явный `@admin_only`

**[CRITICAL] bot/web_admin/core/bulk_ops.py:33,283-292,750-753 — один
глобальный лок на все bulk-инструменты + нет таймаута на сетевые вызовы
Remnawave в двух из пяти путей → зависание блокирует все bulk-операции
навсегда**
`_bulk_ops_lock` — один на всё (delete-expired, delete-empty-uuid, compensate,
retry-failed-payments, clear-devices). Таймаут (`asyncio.wait_for(...,
COMPENSATE_USER_TIMEOUT_SEC)`) поставлен только для `compensate_user_fast`
(строка ~474-477). `delete_user_full` (строка 288, `remnawave_manager_instance
.delete_user`) и `retry_failed_payment` (вызывается из bulk_ops:750-753, внутри
— вызовы `remnawave_manager_instance.update_user_subscription`/
`grant_subscription` без обёртки) не защищены.
**Сценарий:** зависшее TCP-соединение к панели Remnawave во время массового
удаления просроченных клиентов держит `_bulk_ops_lock` захваченным навсегда —
`is_bulk_operation_running()` остаётся `True`, и ни один из пяти bulk-инструментов
больше не запускается. Отменить нечем: механизм отмены (`_bulk_cancel_events`)
нигде не читается — мёртвый код (см. MINOR ниже). Единственный выход — рестарт
процесса web_admin. Это прямой регресс к багу «bulk timeout», который
`docs/state.md` числит исправленным — фикс применён только к одному из пяти
инструментов.
**Фикс:** обернуть сетевые вызовы в `delete_user_full` и `retry_failed_payment`
в `asyncio.wait_for` по аналогии с compensate-путём.

**[CRITICAL] bot/web_admin/run.py:1697-1721 (`secret_static`, `news_media_file`,
`secret_favicon`) — три роута зарегистрированы на `app`, а не на `admin_bp`,
и обходят и аутентификацию, и проверку секретного пути**
`@app.route('/<path:secret>/news_media/<path:filename>')` — параметр `secret`
нигде не сверяется с реальным `ADMIN_SECRET_PATH`, роут не проходит через
`admin_bp.before_request` (там и логин, и IP-whitelist), и `login_required`
на нём тоже нет. Комментарий в коде утверждает «Секретный префикс уже защищает
доступ» (`run.py:1706`) — это неверно: `<path:secret>` матчит любую строку,
то есть `GET /anything-at-all/news_media/<filename>` отдаёт файл без всякой
проверки. Путь traversal перекрыт (`'..' in safe.split('/')`), но сама
экспозиция — нет.
**Сценарий:** файл рассылки (картинка/видео из «Новости»), однажды загруженный,
становится доступен анонимно и без знания секретного пути — достаточно
угадать/узнать дату-папку (`YYYY-MM`) и итоговое имя файла
(`help_<epoch_ms>_<sanitized_name>` — предсказуемая часть, метка времени
не секрет). Данные там не критичные (превью для рассылок), но принцип
защиты, заявленный в коде, фактически не работает — и это тот же паттерн,
которым может «протечь» что-то более чувствительное, если кто-то добавит сюда
следующий роут по аналогии.
**Фикс:** сверять `secret` с `app.config['ADMIN_SECRET_PATH']` и `abort(404)`
при несовпадении, либо перенести роут под `admin_bp` (даст и login, и
whitelist бесплатно) — но тогда придётся решить, нужен ли анонимный доступ
вообще (превью, вероятно, нужен без логина, но с верным секретом).

**[MAJOR] bot/web_admin/templates/base.html:810, login.html:45 (`message|safe`

**[MAJOR] bot/web_admin/core/bulk_ops.py:339-372 (`compensate_user_fast`) —
успешный PATCH в Remnawave + неуспешная запись в SQLite считаются полным
провалом, повтор может урезать уже выданное продление**
Порядок: сначала PATCH `extend_user_expire_at` в Remnawave, потом `UPDATE
users SET subscription_end_date` в SQLite. При `database_locked` (реалистично:
сама функция гоняется с конкурентностью 15 и создаёт нагрузку на ту же
таблицу) функция возвращает `(False, ...)` — оператор видит «failed», хотя
в Remnawave срок уже сдвинут. При повторном запуске compensate для этого же
клиента новый `new_expire` считается от устаревшей (нерассинхронизированной)
`subscription_end_date` в БД, и абсолютный PATCH может выдать клиенту
**меньше** дней, чем уже стоит в Remnawave — молча урезая оплаченное продление.
**Фикс:** различать статусы «rw_ok_db_fail» и «полный provал»; при провале
записи в БД — либо откатывать PATCH в Remnawave, либо перечитывать актуальный
`expire_at` из Remnawave (не из локальной БД) перед следующим расчётом.

**[MAJOR] bot/web_admin/core/bulk_ops.py:174-184,536-539,800 — снэпшот целей
compensate берётся один раз в начале длинной операции, гонка с обычным
продлением клиента**
Список активных клиентов для компенсации кэшируется на весь прогон (может
идти минуты при сотнях клиентов, пакеты по 50, конкурентность 15). Если клиент
в это время продлевает подписку обычным путём (не bulk), bulk-compensate всё
равно применяет абсолютный PATCH, посчитанный от устаревшей даты, и может
откатить Remnawave НАЗАД относительно только что оплаченного продления.
**Фикс:** перечитывать `expire_at` из Remnawave непосредственно перед PATCH
каждого клиента, а не из кэша в начале операции.

command/Tcl-injection через `ssl_domain`/`cert_port`, сейчас недостижимо**
`ssl_domain` без экранирования подставляется и в удалённую shell-команду

**Фикс:** валидировать `ssl_domain` по строгому regex hostname и/или

путь снова подключат к какому-либо роуту.

**[MAJOR] bot/web_admin/core/revoke.py:480-521,620-638 — нет атомарности
между удалением старого Remnawave-пользователя, созданием нового и записью
в БД; при сбое клиент безвозвратно теряет доступ**
Порядок: удалить старого Remnawave-юзера → создать нового (`new_uuid`) →
`UPDATE` в БД (шаг с `asyncio.wait_for(..., timeout=10.0)`). Если шаг записи
в БД падает или зависает после того, как старый уже удалён, `new_uuid` нигде
не сохраняется (кроме SSE-события, которое теряется при обрыве соединения
браузера админа) — клиент полностью и незаметно теряет доступ, без
компенсирующей транзакции и без ретрая. Отдельно: нет lock по `telegram_id` —
два одновременных revoke от разных админов создают два разных `new_uuid` в
Remnawave, финальный `UPDATE` перезаписывается последним, «проигравший»
`new_uuid` остаётся рабочим, но неотслеживаемым в БД доступом.
**Фикс:** писать `new_uuid` в БД тем же шагом/транзакцией, что и создание
в Remnawave (либо через outbox с ретраем), и взять advisory-lock по
`telegram_id` на время revoke.

**[MAJOR] bot/web_admin/routes/remnawave.py:970,991 +

Remnawave, поэтому не CRITICAL, но нарушение — реальное.
**Фикс:** использовать Jinja `|tojson` вместо ручного `json.dumps(...)|safe`.

помечена `Secure` — если админка когда-либо станет доступна по обычному HTTP
(например, ошибка в конфиге Caddy или прямой доступ по IP, который вроде бы
блокируется `_host_is_ip`, но это не то же самое, что форс TLS), кука уйдёт
открытым текстом. Учитывая, что весь трафик рассчитан идти через Caddy с TLS —
риск невысокий, но явный `Secure=True` за реверс-прокси с доверенным
`X-Forwarded-Proto` был бы правильнее.

**[MINOR/подтверждено] `settings_general.html` — `trial_days` поле с
`min="1"` и текстом «Минимум 1 день для пробного периода», хотя триал выключен
(`trial_days=0` в БД).** Сервер (`settings.py:171-226`) значение НЕ
валидирует и НЕ клэмпит — прямой POST (curl) сохранил бы `0` без проблем,
уязвимости в бэкенде нет. Но при обычной работе через браузер: пока в поле
лежит `0`, встроенная HTML5-валидация (`min="1"`) блокирует отправку ВСЕЙ
формы «Основные настройки» (один `<form>` на все ключи) — админ не может
пересохранить никакие ДРУГИЕ настройки на этой странице, не подняв заодно
`trial_days` до ≥1 (случайно реактивировав триал, которого по факту у товара
нет). Как и было в журнале — задача чисто фронтенд/UX, но реально мешающая.
**Фикс:** заменить `min="1"` на `min="0"`, убрать вводящую в заблуждение
подсказку.

**[MINOR] CSRF-токена нет нигде в приложении** (grep по `csrf` не находит
механизма защиты, только упоминание в комментарии `pwa.py:187`).
`SESSION_COOKIE_SAMESITE='Lax'` реально закрывает классический межсайтовый
CSRF для POST-мутаций (Lax не шлёт куку при межсайтовой не-GET навигации), и
side-effect-GET роутов в проверенной зоне не найдено. Остаточный риск — только
через уже описанные XSS (где CSRF-токен всё равно не спас бы) или если
когда-нибудь появится side-effect GET. Указано разово как системная находка.
